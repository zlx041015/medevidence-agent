# 制作流程

这份文档不是抽象方法论，而是建议你真实开发时的顺序。

## 第 1 步：先定义最小任务

### 要做什么

不要一上来做“支持所有疾病、所有指南、所有医院场景”。

先把问题收缩为：

`输入一个临床问题，输出基于证据的简要结论和引用。`

### 为什么这样做

因为实训项目最容易失败的原因不是技术不会，而是范围失控。

如果你的第一版就想同时做：

- 病历结构化
- 文献检索
- 指南对比
- 诊断建议
- 医生端审核
- Web 前端

那大概率每个点都做不深。

### 第一版边界

第一版只做：

- 单轮问题输入
- 候选证据检索
- 结构化抽取
- 简单核验
- 生成回答

## 第 2 步：先画工作流，不先写 Prompt

### 工作流

```text
Clinical Question
   -> Planner
   -> Retriever
   -> Extractor
   -> Verifier
   -> Writer
   -> Final Answer
```

### 为什么先画工作流

因为如果你先写 Prompt，很容易把所有职责塞进一个大提示词里，后果是：

- 输出不稳定
- 很难调试
- 不知道是哪一步出问题
- 无法做模块化评估

拆节点之后，每一步都可以独立看输入输出。

## 第 3 步：先用 mock 数据跑通

### 要做什么

第一版不要急着接真实搜索和网页抓取，先用本地 mock 证据数据模拟整个流程。

### 为什么这样做

真实搜索和网页抓取会带来很多无关复杂度：

- 反爬
- HTML 清洗
- 页面结构变化
- 接口限流

如果你连核心流程都没跑通，就直接接外部数据，调试难度会非常高。

### 你要学到什么

这一阶段主要学：

- 状态流转
- 节点职责
- 参数影响
- 证据和结论之间的映射关系

## 第 4 步：给每个节点定义输入输出

### Planner

输入：
- 用户问题

输出：
- 研究意图
- 检索关键词
- 风险等级

### Retriever

输入：
- 检索关键词

输出：
- 候选来源列表

### Extractor

输入：
- 候选来源内容

输出：
- 结构化证据项

### Verifier

输入：
- 结构化证据项

输出：
- 结论草案
- 置信度
- 冲突说明

### Writer

输入：
- 结论草案
- 证据列表

输出：
- 最终回答
- 引用附录

### 为什么这一步非常重要

因为以后你升级成 LangGraph、FastAPI、前端、数据库时，最稳定的部分就是节点接口。

## 第 5 步：从规则版开始，而不是一开始就全 LLM

### 建议

第一版里：

- Planner 可以规则优先
- Retriever 可以关键词匹配优先
- Verifier 可以先做简单投票或频次统计

### 为什么

因为这样你能更清楚地看出：

- 哪些问题真的是模型能力问题
- 哪些其实是数据和流程问题

如果所有环节都交给 LLM，你会很难定位错误来源。

## 第 6 步：再接入真实模型

当本地流程跑通后，再替换以下模块：

- Planner：改为 LLM 提取问题意图和检索策略
- Extractor：改为 LLM 抽取证据字段
- Writer：改为 LLM 生成自然语言总结

### 为什么不是先替换 Verifier

核验是最敏感的地方。第一版先用规则和显式逻辑，反而更可控。

## 第 7 步：最后再做高级能力

这些能力建议放在后面：

- LangGraph 持久化
- 人工审批 interrupt
- Playwright 网页抓取
- 前端可视化
- Eval 数据集

### 原因

这些能力虽然很重要，但建立在“核心流程稳定”的基础上。

如果前面没打牢，后面只会放大混乱。
