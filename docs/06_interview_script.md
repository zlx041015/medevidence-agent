# 面试讲稿

## 30 秒版本

我做的是一个面向通用常见病症问题的证据驱动型医学 Agent 原型。它不是直接让大模型回答医学问题，而是先基于医学来源做检索，再完成问题规划、证据抽取、核验和总结输出，并通过 verifier 控制风险。现在项目已经从 demo 升级成带 benchmark、baseline 对比、消融实验和结果导出的完整系统。

## 2 分钟版本

这个项目的核心目标是解决医疗场景下“大模型直接回答不可靠”的问题，所以我把系统拆成几个明确阶段：`Planner`、`Retriever`、`Extractor`、`Verifier` 和 `Writer`。

项目最早是规则版 workflow，用来验证整体结构；之后接入了 LLM 节点和 PubMed 适配器；最新一版则从专项病种示例进一步升级成了“面向通用常见病症问题的医学证据系统”，补齐了 benchmark 数据结构、baseline 对比、消融实验、多病种来源、增强 verifier 和图形界面。

现在系统可以完成这样一条主链：用户输入一个通用病症问题后，`Planner` 生成检索计划，`Retriever` 从 mock、多源 mock 或 PubMed 适配器取回来源，`Extractor` 抽取结构化证据，`Verifier` 从主题一致性、证据支撑、来源等级、冲突检测和时间有效性几个维度做核验，最后 `Writer` 输出结构化结论。同时我还补了实验 runner，可以批量比较不同方法，并导出总表和成功/失败案例。

## 架构亮点

### 1. 为什么不是直接医学问答

因为医疗场景更需要可追溯和可解释。直接问答虽然简单，但很难说清证据从哪里来，也不容易控制幻觉。

### 2. 为什么采用多阶段工作流

我把任务拆成多个节点，是为了让每一步职责清晰、便于调试，也便于后续做消融实验和评测。

### 3. 为什么 verifier 是重点模块

这个项目里我最想强调的不是“大模型能回答”，而是“系统能不能在医疗场景下约束回答”。所以 verifier 不只是打分，还会输出主题覆盖、支撑强度、证据等级、时间有效性和冲突检查结果，让结果更可解释。

## 面试常见追问

### Q1. 这算不算 RAG？

算轻量 RAG。它已经具备真实来源适配、切块、chunk 级检索和基于证据回答的主链，但还不是重型向量数据库平台。

### Q2. 你这个项目最新一轮升级的重点是什么？

重点是从单一专项示例升级成“面向通用常见病症问题的系统原型”，也就是说它不再只适合讲个别病种，而是开始具备通用性。

### Q3. 你怎么控制幻觉？

我主要用了几层策略：

- 不直接回答，先检索来源
- 抽取节点只做结构化证据抽取
- verifier 做显式核验和人工审核提示
- writer 只基于已核验内容组织输出

### Q4. 如果继续做下去，你会补什么？

我会优先补三块：

- 扩大 benchmark 并增加人工盲评
- 接入更多真实在线来源
- 用更强的 reranker 和 judge model 增强评测与核验能力

## 简历要点草稿

- 设计并实现面向通用常见病症问题的证据驱动型医学 Agent 工作流，将问题处理拆解为规划、检索、抽取、核验与总结五个阶段。
- 自建 benchmark 数据结构，搭建 baseline 对比与消融实验框架，支持自动评测、失败案例分析和结构化结果导出。
- 构建多病种来源检索与增强 verifier，通过主题一致性、来源等级、冲突检测和时间有效性检查提升系统可解释性与安全性。
