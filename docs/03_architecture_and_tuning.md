# 架构与调参

这份文档专门回答两个问题：

1. 你为什么这样设计架构
2. 当结果不理想时你应该调什么

## 一、为什么采用“工作流主导”架构

### 不推荐的做法

一个大 Prompt 直接做：

- 理解问题
- 搜索资料
- 比较指南
- 生成结论

### 问题

- 难调试
- 难追踪错误
- 很难保留证据链
- 结果不稳定

### 推荐做法

把流程拆成五个独立节点：

1. `Planner`
2. `Retriever`
3. `Extractor`
4. `Verifier`
5. `Writer`

### 背后原因

这叫做把“生成问题”转成“状态机问题”。

AI 应用工程的关键不是提示词写得多花，而是：

- 能否定义状态
- 能否约束节点职责
- 能否记录中间结果
- 能否失败恢复

## 二、当前代码里的关键参数

你会在配置里看到这些参数。

### `top_k`

作用：
- Retriever 最多保留多少条候选来源

为什么需要它：
- 候选太少，容易漏信息
- 候选太多，噪声会进入后续节点

建议：
- Demo 阶段先用 `3`
- 真实场景一般从 `5` 到 `8` 开始试

调参方法：
- 如果结论经常漏关键信息，增大 `top_k`
- 如果回答变乱、引用变杂，减小 `top_k`

### `evidence_score_threshold`

作用：
- 过滤掉太弱的证据

为什么需要它：
- 医疗场景里，弱相关资料不能直接混进答案

建议：
- mock 阶段先用 `0.55`
- 如果真实搜索质量差，可以先提高到 `0.65`

调参方法：
- 如果系统经常引用边缘资料，提高阈值
- 如果系统总是找不到足够证据，降低阈值

### `confidence_threshold`

作用：
- Verifier 判定结论是否足够可靠

为什么需要它：
- 不是所有问题都应该被系统“强答”

建议：
- 第一版先用 `0.70`

调参方法：
- 如果输出太保守，经常说“证据不足”，降低一点
- 如果输出太激进，经常直接下结论，提高一点

## 三、为什么 Verifier 尽量不用纯生成式

很多初学者会让模型直接说：

`请综合以上资料给出最可靠答案`

这会有一个问题：

- 模型会把“措辞流畅”误当成“事实可靠”

所以第一版建议把 Verifier 做成：

- 统计支持某结论的证据数
- 考虑来源分数
- 检测冲突描述
- 最后给出置信度

### 背后原因

核验最好先显式化，再让模型参与润色，而不是把核验全黑箱化。

## 四、什么时候引入 LLM 调参

### Planner 调参

你需要重点调：

- system prompt 是否明确强调“不要直接回答问题，只生成检索计划”
- 输出结构是否严格 JSON 化
- 是否限制关键词数量

为什么：
- Planner 如果越界直接回答，会污染整个流程

### Extractor 调参

你需要重点调：

- 是否规定字段名
- 是否要求保留证据原句
- 是否要求输出发布时间和来源类型

为什么：
- 抽取节点是后面所有核验的基础

### Writer 调参

你需要重点调：

- 是否禁止脱离证据自由发挥
- 是否要求显式说明“不确定性”
- 是否强制附上引用编号

为什么：
- 医疗场景最怕看起来流畅但没有依据

## 五、架构升级路径

### 阶段 1：本地顺序工作流

目的：
- 看懂全流程
- 能跑、能调、能讲

### 阶段 2：接入真实 LLM 与搜索

目的：
- 提升真实效果
- 开始形成项目亮点

### 阶段 3：升级成 LangGraph

目的：
- 做持久化
- 做中断恢复
- 做人工审批

### 阶段 4：接入前端和评测

目的：
- 提升展示效果
- 让项目更像真实产品

## 六、你面试时要讲的架构选择理由

推荐说法：

`我没有一开始做高度自治的多智能体协商，而是采用工作流主导的节点式架构，因为医疗问题对可解释性和稳定性要求更高。先把检索、抽取、核验、生成拆开，能更容易定位错误和建立证据回溯机制。`
